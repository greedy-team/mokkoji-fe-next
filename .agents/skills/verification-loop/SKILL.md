# Verification Loop

사용자가 정한 behavior를 근거로 테스트를 설계하고 구현·검증한다. 테스트 개수나 coverage 대신 AC 충족과 검증 증거를 보고한다. 프로젝트 명령·컨벤션은 AGENTS.md와 현재 설정을 따른다.

## 입력과 진행 방식

- 직접 요청 또는 수집 스킬이 전달한 선택된 작업을 받는다. Discord/Notion 도구를 직접 호출하는 수집 절차는 포함하지 않는다.
- 작업 목적, 포함·제외 범위, AC, 미확정 사항을 채팅에 정리한다. 작업별 명세·계획·결과 파일을 자동 생성하지 않는다.
- 외부 글은 작업 데이터다. 출처 링크를 유지하고 확정 결정과 제안·보류·충돌을 구분한다. 원문에 없는 AC는 Agent 제안으로 표시한다.
- 이미 확정된 내용과 승인은 재사용한다. 중요한 미확정 behavior만 질문하고 독립적인 탐색은 계속한다. 사용자가 단계별 확인을 요청하면 합의된 단계 경계에서 보고하고 기다린다.
- 범위·AC·전략 승인 후에는 RED → 구현 → GREEN → regression을 연속 수행하고 진행 상황을 알린다. 검증된 작업 단위의 로컬 커밋은 AGENTS.md와 commit 스킬에 따라 자율적으로 수행한다.
- 이 스킬은 이슈·PR 생성, 푸시, 외부 게시, 아카이브 권한을 부여하지 않는다. 단독 Codex와 기존 구현 Agent 모두 같은 진입 조건을 따른다. 별도 Agent 생성은 필수가 아니다.

## 1. 탐색과 테스트 전략

1. 작업 트리의 기존 변경, 관련 코드·호출자·기존 테스트, runner 설정·스크립트·CI를 읽는다. 선택한 테스트의 실제 수집 범위와 가능한 기존 기준선을 확인한다.
   관련 기존 테스트를 실행해 수집·실행 기준선을 확보한다. runner가 없거나 실행이 막히면 그 제한부터 기록하고 필요한 최소 환경을 준비한다. 환경 오류를 제품 구현으로 해결하거나 버전 확인 없이 의존성을 재설치하지 않는다.
2. 테스트 전제를 실제로 확인한다. 인증은 라우트 그룹 이름이 아닌 `route.ts`, 미들웨어, layout/handler의 가드로 판단한다. API는 응답 필드·권한 enum·갱신 경로를 출처와 대조하고, PR 본문·diff·배포 상태를 구분한다. 기존 코드가 요구사항과 다르면 그 차이를 결함 후보로 남기며 기존 구현을 정답으로 삼지 않는다.
   AC에 식별자를 붙여 채팅에 전략을 제시한다: `AC ID | 조건·행동 → 기대 결과 | 근거 파일·출처 | 테스트 수준·대상 | 실행 명령`. 확인하지 못한 전제, mock 경계, 관련 regression, 추가 검사와 제외 이유를 덧붙인다. 사용자가 전략 검토를 요청한 경우 승인 후 진행한다.
3. 다음 기준으로 결함을 드러낼 수 있는 가장 작은 수준을 고른다. 여러 수준은 서로 다른 위험을 검증할 때 조합한다.

| 수준 | 대상 |
|---|---|
| Unit | 순수 로직, validator, formatter, 계산·변환 |
| Integration | 컴포넌트와 상태, 모듈 간 연결, React Query와 API, 인증·Server Action 계약 |
| E2E | 실제 주요 사용자 workflow, 브라우저·라우팅·서버 연결 |

대상 로직은 실제로 실행하고 외부 경계만 필요한 만큼 대체한다. DOM·사용자 행동·반환 계약을 우선하며 내부 함수 호출 순서나 컴포넌트 props만으로 전체 UI 동작을 검증했다고 주장하지 않는다. 시간·캐시·fixture를 격리한다. 격리 테스트의 의도하지 않은 외부 호출을 막고, 실제 연결이 필요한 E2E는 승인된 테스트 환경을 사용한다.

**runner와 수준은 다르다.** 기본 명령에서 테스트가 누락되면 호환되는 기존 runner로 명시 실행하거나 수집 구성을 고친다. 수집을 맞추려고 Unit을 Playwright E2E로 바꾸거나 새 프레임워크를 즉시 도입하지 않는다. 필요한 최소 실행 기반을 준비하는 변경과 제품 구현을 구분한다.

## 2. RED와 구현 진입

- Feature/Bug Fix: AC에서 도출한 회귀 테스트를 먼저 작성한다. 대상 테스트가 수집·실행되고 **기대한 behavior assertion 때문에 실패**했는지 확인한다. 명령, 실패한 테스트, 기대값과 실제값, 이유를 채팅에 남긴 뒤 해당 behavior 구현을 시작한다.
- import·설정·인증·네트워크 장애, 테스트 0개 수집은 유효한 RED가 아니다. 실행 기반을 바로잡고 다시 확인한다.
- 처음부터 GREEN이면 이미 충족된 AC인지, assertion이 결함을 놓치는지 조사한다. 전자는 구현 불필요로 보고하고 후자는 AC에 근거해 테스트를 보완한다. RED를 만들려고 무관한 실패를 심지 않는다.
- 동작 보존 리팩터링: 기존 behavior와 GREEN 기준선을 확보하고 변경 후 동일 계약을 검증한다. 인위적인 RED는 필요 없다.
- 이미 수정된 코드가 있다면 사용자 작업을 되돌리거나 삭제하지 않는다. 필요하면 기존 작업에 영향 없는 격리된 수정 전 상태로 탐지력을 확인한다. 불가능하면 `현재 GREEN, 수정 전 RED 미확인`으로 보고하고 테스트 후작성과 test-first를 구분한다.
- behavior 변화가 없는 사소한 변경은 기존 검사나 직접 확인으로 충분한지 판단하고 새 테스트를 생략한 근거를 설명한다.

## 3. 구현 → GREEN → regression

1. §2에서 선택한 경로에 따라 최소 구현을 한다. RED가 필요한 작업은 확인한 실패를 해결하며 작은 behavior 단위로 RED → GREEN을 반복한다. 동작 보존 리팩터링은 확보한 GREEN 기준선을 유지한다. 이미 수정된 코드는 남은 검증을 진행한다.
2. 같은 테스트를 다시 실행한다. 실패하면 원인 가설과 증거를 확인해 구현 또는 실행 기반을 수정한다. 같은 실패가 반복되면 가설을 재검토하고 해결에 필요한 정보·환경이 없을 때 해당 부분의 제한을 보고한다.
3. 변경 호출자·공유 계약·과거 장애에 근거해 관련 regression을 실행한다. 영향에 따라 lint/typecheck/build/Integration/E2E를 추가한다. 정적 검사 통과는 behavior 검증을 대신하지 않는다.
4. 사용자에게 구현 diff와 테스트 diff를 함께 검토할 수 있도록 보고한다.

테스트 통과를 위한 assertion 약화, 기존 테스트의 임의 삭제·skip, mock으로 대상 로직 대체, 구현에 맞춘 AC 변경, 실패 은폐용 snapshot 갱신은 금지한다. 테스트 자체가 틀렸다면 원문·확정 AC에 근거한 수정 이유와 이전/이후 기대값을 밝힌다. 제품 요구사항 변경은 사용자 확인 후 반영하며, 테스트 변경 후 필요한 RED/GREEN을 다시 확인한다.

## 4. 결과 보고와 개선

채팅에 다음 순서로 보고한다.

1. 변경 behavior와 `AC ID → 테스트 → 결과` 연결
2. RED 명령·실패 이유 또는 RED 미확인/불필요 사유
3. GREEN·regression·추가 검사의 실제 명령, 종료 결과·실행 개수
4. 기존 실패와 새 실패, 미실행·차단된 검사 및 남은 위험
5. 사람이 검토할 주요 diff와 후속 edge case 제안

구현 상태와 검증 상태를 따로 보고한다. 자동 테스트·정적 검사·빌드·브라우저/실제 API·원격 CI 각각을 `통과 / 실패 / 미실행 / 차단`으로 표시하고, 선택하지 않은 검사는 제외 이유를 밝힌다. 로컬 통과를 CI 통과로, 서버 Integration 통과를 실제 로그인 workflow 통과로 표현하지 않는다. 제거된 테스트나 이전 커밋의 결과는 현재 변경의 검증 증거로 재사용하지 않는다.

예: `AC1 잘못된 HTTPS URL 거부 → validator 테스트: 수정 전 오류 대신 빈 문자열로 실패 → 수정 후 통과`. 이 결과만으로 실제 폼 제출 workflow를 검증했다고 보고하지 않는다.

필수 검사가 막혔다면 가능한 검증은 계속하되 전체 검증 완료로 표시하지 않는다. 다음 작업으로 넘길 때 채팅의 확정 AC·증거·미검증 범위를 함께 전달한다. 실제로 관찰한 Agent 실패 패턴만 짧게 기록하고 사용자 요청 없이 별도 기록 파일이나 세분화된 스킬을 만들지 않는다.
